# AI UI Slop Bot Requirements

Status: **Audit-hardened discovery specification; validation pending**

Public product name: **AI UI Slop Bot**
CLI and GitHub Action identifier: **`ai-ui-slop`**
Technical subtitle: **Deterministic aesthetic-convergence scanner for React**

## 1. Product intent

AI UI Slop Bot scans a codebase for repeated, context-insensitive frontend patterns that make a product resemble generic vibe-coded web applications. It reports evidence and Preservation Obligations an engineer or coding agent can use to restore deliberate hierarchy and product identity while independently verifying that application behavior did not regress.

This project takes the private initial design brief for **Bot 2: The React UI Scanner** as research material. Claims, proposed technologies, example weights, thresholds, and timelines from that brief are hypotheses to test rather than requirements or authoritative evidence. The brief is deliberately not part of the repository.

The bot is a critic, not an autonomous designer. It identifies suspicious combinations and explains them. It does not claim to prove that code was generated by AI, and it does not equate any single technique, such as a gradient or rounded corner, with poor design.

**[INTENT-001]** Public documentation may use the memorable “slop” terminology but shall define it through the domain glossary and shall not accuse a contributor, repository, or component of AI authorship.

The canonical domain definition of **AI UI Slop** is maintained in `CONTEXT.md`. The enforcement target is aesthetic convergence: looking like interchangeable vibe-coded web applications. Authorship is irrelevant.

### 1.1 Normative language

**[NORM-001]** `Shall` identifies a mandatory, verifiable requirement. Numbered MVP and Full V1 acceptance criteria are also mandatory release gates despite using imperative wording. `Must` inside an identified requirement or acceptance criterion has the same mandatory force; `should` expresses a recommendation whose omission requires documented rationale; `may` grants permission rather than imposing work.

**[NORM-002]** Examples, candidate lists, provisional hypotheses, working assumptions, and explanatory prose are non-normative unless an identified requirement explicitly incorporates them. Phrases such as “where practical” or “where applicable” shall not waive a mandatory gate unless the same requirement defines the deciding condition and required evidence.

## 2. Goals

- Scan an entire repository, not only a pasted component or a pull-request diff.
- Make the Validated MVP useful for cleaning an existing repository by producing an actionable report for a coding agent.
- Analyze React UI structure and styling with deterministic, explainable rules.
- Detect combinations and repetition that are more meaningful than isolated style choices.
- Enforce resistance to generic AI-default aesthetics while allowing deliberate use of the same individual techniques.
- Produce concise human-readable diagnostics for developers.
- Produce stable, structured output that a coding agent can act on.
- Support repository-specific design intent so acceptable patterns can be distinguished from unwanted ones.
- Run locally and in continuous integration without requiring an LLM.
- Estimate likely customer satisfaction before implementation by testing whether intended users judge the proposed findings as accurate, actionable, and worth acting on.

## 3. Non-goals for the Validated MVP

- Determining whether a person or an AI authored the code.
- Assigning an objective aesthetic quality score to a whole product.
- Automatically redesigning or modifying source files.
- Rendering pages and judging their appearance from screenshots.
- Analyzing prose or UI copy for AI-like wording; that belongs to Bot 1 in the source document.
- Replacing accessibility, linting, formatting, or type-checking tools.
- Performing whole-program prop-drilling analysis until its useful signal and cost are established.
- Ranking unrelated repositories by aesthetic quality or AI Slop Score.

### 3.1 Delivery milestones and requirement gates

**[MILESTONE-001]** The project shall distinguish evidence-gathering work from releasable product scope. A requirement applies only at the milestone named below or when its text explicitly assigns it to a later milestone.

1. **[MILESTONE-002]** **Discovery Prototype, an unreleased experiment:** Prove the highest-risk technical and product hypotheses with the Repeated Decorative Shell rule on representative React/TSX, Tailwind, and static-inline-style fixtures. The prototype shall exercise local advisory scanning, source evidence, interactive progress reporting, and draft JSON and Markdown output. It is disposable, may support only the benchmark platform, and is not required to satisfy MVP or Full V1 compatibility, distribution, enforcement, corpus, or platform gates.
2. **[MILESTONE-003]** **Validated MVP (first usable release):** Deliver a whole-repository local advisory scanner with Repeated Decorative Shell and Effect Stacking, the explicitly bounded MVP House Style configuration, canonical JSON, a generated Markdown Refactoring Brief, and a native Linux x86-64 binary. It shall prove that intended users find the results sufficiently accurate, actionable, and worth using. It does not include baseline enforcement, GitHub integration, broad Page Archetype coverage, the remaining seven-rule pack, or the Full V1 platform matrix.
3. **[MILESTONE-004]** **Full V1:** Deliver the complete eleven-rule pack, all built-in Page Archetypes plus safe generic fallback and taxonomy extension, all specified Tailwind v3/v4 and static inline-style analysis, monorepository Analysis Scopes, Reviewed Baselines, whole-repository regression enforcement, the GitHub Action, and every supported native target. Full V1 shall satisfy all requirements and acceptance criteria labeled V1 unless explicitly deferred.

Changed-file-only presentation, inline pull-request annotations, and a hosted GitHub App are post-V1 capabilities. Full V1 enforcement evaluates whole-repository results against a Reviewed Baseline and may return exit code 1 for policy-violating new or materially worsened Findings.

**[MILESTONE-005]** The V1 feature boundary is bounded, non-executing static analysis. Runtime CVA selections, additional static recognition of arbitrary render-transforming higher-order components or plugin-provided Tailwind semantics, a general CSS cascade, CSS Modules, and CSS-in-JS analysis are explicitly post-V1 candidates. Executing target configuration or plugins remains prohibited. Encountering unsupported forms shall produce unresolved coverage where they could affect a result; their exclusion shall not be represented as successful analysis.

**[MILESTONE-006]** A build that implements this bounded feature surface and passes local verification is a **V1 Implementation Candidate**, not Full V1. Hosted native-target qualification, committed reference-runner performance evidence, authenticated release verification, required fuzz and mutation evidence, and customer calibration remain mandatory Full V1 release gates and shall not be described as deferred features.

**[MILESTONE-007]** Within the documented static-resolution and resource bounds, the following are V1 Implementation Blockers rather than post-V1 enhancements: semantic extraction from relevant static Tailwind v3 theme values and v4 theme/custom-utility declarations; reachability reasoning for supported container, feature-query, and custom variants; symbol-aware named and wildcard re-export provenance; and component-level impact attribution for supported shared primitives. Inputs that exceed the documented bounds may remain unresolved only when the scanner reports the resulting coverage loss as required elsewhere in this specification.

## 4. Users and use cases

### Primary users

- **Validated MVP:** a repository maintainer reviewing an existing frontend and a coding agent consuming Findings before refactoring UI code.
- **Full V1:** a developer or maintainer checking repository regressions in continuous integration or a pull request.

During discovery, the project owner is the initial Design Authority and customer proxy.

### Core use cases

1. In the Validated MVP, a maintainer scans an existing React repository and gives the resulting report to a coding agent for a behavior-preserving UI cleanup.
2. In Full V1, a developer runs the scanner in CI and fails the check only when Findings violate the repository's configured policy.
3. A coding agent reads structured findings containing locations, evidence, triggered rules, and remediation constraints.
4. A team tunes, disables, or suppresses rules to reflect its design system rather than accepting a universal aesthetic.

## 5. Scope of analysis

### Initial source scope

**[SCOPE-001]** The Validated MVP shall analyze:

- JavaScript and TypeScript React files using `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts`, `.cjs`, and `.cts` extensions.
- Statically discoverable JSX elements, components, attributes, and nesting.
- Literal styling data, including static `className` strings and statically resolvable class composition supported by the chosen parser.
- Repository-local configuration and suppression directives.

**[SCOPE-002]** The scanner shall skip generated, vendored, dependency, build-output, and explicitly ignored paths by default.

### Initial styling scope

**[STYLE-001]** The Validated MVP shall support Tailwind CSS classes in the supported React source forms. Tailwind is the first styling vocabulary, not a permanent product boundary.

**[STYLE-002]** V1 shall support Tailwind v3 and v4 utility vocabularies and configuration models. It shall infer the likely version from repository manifests and lockfiles without installing dependencies and shall allow explicit version configuration when detection is absent or ambiguous.

**[STYLE-003]** For Tailwind v3, the scanner shall safely interpret statically declared relevant values in `tailwind.config.js`, `.cjs`, `.mjs`, or `.ts` without importing or executing the file. Dynamic expressions, plugins, required modules, or computed configuration shall remain unresolved coverage.

**[STYLE-004]** For Tailwind v4, the scanner shall parse relevant CSS-first configuration including `@theme`, `@source`, `@utility`, and custom-variant declarations. It shall resolve only repository-internal static CSS imports. External, dynamic, unsupported, or cyclic CSS configuration shall remain unresolved coverage.

**[STYLE-005]** The Tailwind adapter shall report the detected or configured version, configuration sources, unresolved constructs, and resulting style-resolution effect.

**[STYLE-006]** The adapter shall parse arbitrary values, arbitrary properties, variants, and CSS-variable references into semantic signal categories when statically possible. Examples include classifying an arbitrary radius by magnitude or an arbitrary shadow by its declared layers and spread.

**[STYLE-007]** Use of arbitrary syntax shall never contribute directly to the AI Slop Score. An arbitrary value that cannot be interpreted safely shall reduce style-resolution coverage or Finding Confidence rather than receive a guessed penalty.

**[STYLE-008]** Responsive, interaction-state, theme, container, feature-query, and custom-variant conditions shall remain attached to extracted signals. Pattern evaluation shall combine only signals that can coexist in a reachable state.

**[STYLE-009]** The scanner shall not merge mutually exclusive breakpoints, themes, branches, or variant conditions into one decorative cluster. Each state-dependent Finding shall report the relevant condition set, such as `dark + lg + hover`. Uncertain reachability shall lower Finding Confidence or style-resolution coverage.

**[STYLE-010]** Reachability shall use a symbolic condition model rather than enumerating every possible rendered state. The analyzer shall simplify compatible and contradictory constraints and shall impose documented rule-specific complexity limits.

**[STYLE-011]** When condition complexity exceeds a limit, the scanner shall report the affected expression and coverage loss. It shall not silently truncate branches or select an arbitrary representative state.

**[STYLE-012]** Style extraction shall be separated from rule evaluation through a stable internal signal model. Adding CSS Modules, stylesheet analysis, CSS-in-JS, or another styling system later should require a new extractor or adapter rather than reimplementing the rules. Structural React rules shall remain usable without Tailwind.

**[STYLE-013]** V1 shall also extract semantic style signals from literal React `style` objects, statically resolvable shared style objects, and statically assigned CSS custom properties. Relevant gradients, shadows, blur, radii, borders, spacing, positioning, and other supported effects shall map to the same internal signals as equivalent Tailwind utilities.

**[STYLE-014]** Runtime-computed inline values shall remain unresolved coverage. V1 shall not implement a browser cascade or general stylesheet-selector engine as part of inline-style support.

**[STYLE-015]** Dynamic styles that cannot be resolved safely shall be reported as unanalyzed coverage, not guessed at or silently treated as clean.

**[STYLE-016]** All scanned repository content shall be treated as untrusted data. V1 shall not install target dependencies, run package scripts, build or render the target application, import target modules, execute Tailwind configuration, or evaluate arbitrary expressions to improve analysis.

## 6. Detection model

### 6.1 Principles

- **[DETECT-001]** A single rounded corner, shadow, gradient, or decorative effect shall not by itself label a component as slop.
- **[DETECT-002]** Rules shall evaluate context, combinations, intensity, density, nesting, repetition, and repository policy where applicable.
- **[DETECT-003]** Every Finding shall be reproducible from source, configuration, declared Analysis Scope, scanner version, rule-pack version, and schema version.
- **[DETECT-004]** Every score shall be decomposable into named rule contributions.
- Scores express policy risk or review priority, not certainty about authorship or design quality.
- **[DETECT-005]** Analysis shall consider repository-wide repetition because aesthetic convergence can emerge from individually acceptable elements used everywhere.
- **[DETECT-006]** A repository's House Style shall provide positive evidence of deliberate identity; the scanner cannot define distinctiveness only as the absence of gradients, rounding, shadows, cards, or pills.
- **[DETECT-007]** Importing or using a particular UI library shall never contribute directly to the AI Slop Score. Library identity may assist structural role resolution only.

### 6.2 V1 rule pack

**[RULE-001]** Every Slop Pattern shall have a versioned **Rule Contract** completed and approved before implementation of that rule begins. A Rule Contract shall define:

- its exact analysis entity, actionable owner, and aggregation scope;
- required signals, supporting signals, and exclusions;
- activation, interaction, saturation, and capping logic;
- acceptable counterexamples and the precise effects of House Style approval;
- its score contributions and its effects, if any, on Repository Profile aggregation;
- confidence and Analysis Coverage behavior for partially resolved evidence;
- stable evidence fields and remediation constraints emitted in reports;
- positive, acceptable-negative, boundary, interaction, and unresolved-input Calibration Cases.

**[RULE-002]** A descriptive rule name and intent do not satisfy this gate. Provisional weights and thresholds may remain calibration data, but the calculation shape, evidence contract, and behavior at boundaries shall be explicit and testable. Contract changes that can alter Findings, scores, or fingerprints shall follow rule-pack versioning and migration requirements.

**[RULE-003]** The Discovery Prototype shall implement only Repeated Decorative Shell. The Validated MVP shall implement Repeated Decorative Shell and Effect Stacking. All eleven Rule Contracts shall be approved before Full V1 rule implementation begins, and Full V1 shall ship all eleven rules.

**[RULE-004]** V1 shall include these Slop Patterns:

- **Repeated Decorative Shell:** recurring over-decorated display-container treatments across otherwise distinct components.
- **Template Convergence:** stock page formulas interpreted within a Page Archetype.
- **Effect Stacking:** several high-intensity decorative effects coexisting on one reachable element or tightly coupled group.
- **Decoration Saturation:** one decorative treatment repeated until it overwhelms meaningful hierarchy within a component or page.
- **Shape Homogenization:** the same conspicuous pill or rounded silhouette applied indiscriminately across different UI roles.
- **Cardification:** content divided into unnecessary nested or repetitive floating containers until cards replace meaningful grouping.
- **Generic Container Depth:** deep non-semantic wrapper hierarchies coupled with decorative layering; depth alone is insufficient.
- **Design Token Drift:** repeated visual values diverging from the approved House Style scale; arbitrary syntax or a single exception is insufficient.
- **Rhythm Homogenization:** excessively uniform spacing, sizing, and section or component rhythm that erases meaningful distinction.
- **Framework Default Convergence:** a stock framework palette and component recipe recurring across otherwise distinct owners.
- **Control Surface Homogenization:** compact outlined surface chrome recurring across controls, content, and structural roles until hierarchy is flattened.

**[RULE-005]** Prop drilling, raw class-string length, package identity, arbitrary-value syntax by itself, and conflicting or redundant utilities shall not contribute to the AI Slop Score. They are architectural, syntactic, or lint concerns rather than reliable evidence of aesthetic convergence.

### 6.2.1 First vertical-slice rule: Repeated Decorative Shell

**[RULE-SHELL-001]** The first implemented rule shall identify local decorative-shell candidates, but a candidate shall not become a Repeated Decorative Shell Finding until a substantially similar shell satisfies the Rule Contract's calibrated recurrence threshold across distinct component owners. Once the threshold is met, each participating actionable owner may receive a Finding linked to the same recurrence cluster.

Candidate signal categories include:

- extreme corner rounding;
- gradient, glow, or saturated accent treatment;
- large or layered shadows;
- backdrop blur or glass treatment;
- decorative borders or rings;
- unusually generous card-like padding;
- floating or detached container treatment.

**[RULE-SHELL-002]** Exact signals, weights, similarity criteria, and thresholds remain calibration questions. The rule shall include legitimate fixtures such as modal surfaces, intentionally repeated design-system primitives, compact interactive pills, and restrained cards as counterexamples.

**[RULE-SHELL-003]** Discovery mockups shall use this provisional component-band behavior:

- one decorative signal category remains `minimal`;
- two compatible categories normally remain `low`;
- three distinct, meaningful categories reach `moderate`;
- four strongly expressed categories reach `high`;
- five or more coordinated categories may reach `dominant`;
- signal intensity and cross-category interaction adjust the score within or, when supported by Calibration Cases, across a band.

**[RULE-SHELL-004]** Raw utility count shall not determine the band. Recurrence is required for Finding eligibility and contributes to the Repository Profile, but the number of recurrences shall not change a participating component's intrinsic AI Slop Score.

### 6.2.2 Second MVP rule: Effect Stacking

**[RULE-EFFECT-001]** Effect Stacking shall be the Validated MVP's second rule. It provides a component-local test of contextual co-occurrence that complements Repeated Decorative Shell's cross-component recurrence without making MVP viability depend on Page Archetype classification.

**[RULE-EFFECT-002]** The rule shall require multiple distinct, high-intensity decorative signal categories on one reachable UI element or a contractually defined tightly coupled element group. It shall not trigger from raw utility count, several low-intensity declarations, mutually exclusive states, or the mere presence of individually acceptable effects. Its complete Rule Contract and Calibration Cases remain a prerequisite to implementation.

### 6.2.3 Page-level pattern: Template Convergence

**[RULE-TEMPLATE-001]** V1 shall also evaluate page composition. Candidate structural signals include an eyebrow pill, centered promotional hero, gradient headline, paired calls to action, oversized framed product image, bento grid, and generic three-card feature section.

**[RULE-TEMPLATE-002]** No individual section or structure shall trigger Template Convergence. The rule shall require a calibrated combination of distinct stock structures and shall explain which combination matched. Legitimate counterexamples shall include conventional structures given distinctive content hierarchy, brand treatment, interaction, or composition.

**[RULE-TEMPLATE-003]** Discovery mockups shall use provisional combination behavior parallel to Repeated Decorative Shell: one stock structure remains `minimal`, two may be `low`, three coordinated structures become `moderate`, four become `high`, and five or more may become `dominant`.

**[RULE-TEMPLATE-004]** The structures must participate in one recognizable page formula rather than merely coexist somewhere on a page. Distinctive hierarchy, interaction, content shape, composition, or approved House Style treatment shall mitigate the pattern when supported by Calibration Cases.

**[RULE-TEMPLATE-005]** V1 shall provide broad Page Archetype coverage rather than intentionally limiting Template Convergence to marketing pages and dashboards. The built-in taxonomy shall cover at least:

- marketing and product landing pages;
- dashboards and analytics;
- authentication and account recovery;
- onboarding and setup;
- settings, profiles, and account management;
- pricing, plans, and billing;
- commerce catalog, product, cart, and checkout;
- portfolios and showcases;
- documentation, articles, and other content-heavy pages;
- administrative and data-management interfaces;
- search and results;
- social, community, messaging, and activity views;
- forms and multi-step workflows;
- empty, loading, error, and success states.

**[RULE-TEMPLATE-006]** The taxonomy shall be open and extensible. Pages that do not match a named archetype shall still receive generic decorative, repetition, and composition analysis; they shall be labeled `unknown` rather than excluded or forced into the closest archetype.

“Broad Page Archetype coverage” does not claim an exhaustive enumeration of every possible page purpose. V1 satisfies the requirement by providing the built-in catalog, allowing taxonomy extensions, and applying generic analysis safely when classification is unknown.

**[RULE-TEMPLATE-007]** Archetype selection, confidence, and evidence shall be visible in each relevant Finding. Discovery gates and calibration results shall be reported per archetype so strong performance on common landing pages cannot hide weak coverage elsewhere.

**[RULE-TEMPLATE-008]** When several Page Archetypes apply, the scanner shall evaluate and explain each independently. The route component's Component Profile shall use the strongest supported Template Convergence Finding plus only capped breadth from distinct additional Findings; it shall not sum complete archetype scores or duplicate shared signals.

### 6.3 Scoring, confidence, and policy

- **[SCORE-001]** A Slop Signal shall expose its category, resolved value or classification, intensity when applicable, source evidence, and reachable-state conditions. A Slop Signal shall not have an AI Slop Score.
- **[SCORE-002]** A Finding shall represent exactly one Slop Pattern, one actionable owner, and one compatible reachable-state family. Each Finding shall expose a 0–100 AI Slop Score derived from named signal and interaction contributions defined by that rule's Rule Contract.
- **[SCORE-003]** A Component Profile shall aggregate the Findings owned by one React component. Its 0–100 AI Slop Score shall emphasize the strongest Finding and add only capped breadth from distinct additional Slop Patterns.
- **[SCORE-004]** A page shall not introduce a separate scoring entity. A route-owned page component shall use a Component Profile and may own page-composition Findings such as Template Convergence.
- **[SCORE-005]** A Repository Profile shall aggregate Component Profiles using bounded prevalence, recurrence, and distribution terms. It shall expose a 0–100 AI Slop Score without summing component scores.
- **[SCORE-006]** An Analysis Scope shall be the hard score-comparison and aggregation boundary. A top-level monorepository report may list multiple Analysis Scopes but shall not blend their scores into a monorepository AI Slop Score.
- **[SCORE-007]** The normalized score shall range from 0 to 100, where a higher value means stronger aesthetic convergence under the active scanner version and policy.
- **[SCORE-008]** Component scores shall summarize evidence within an actionable refactoring unit. The repository score shall incorporate distribution, density, and recurrence across components rather than merely averaging component scores.
- **[SCORE-009]** Score composition shall be nonlinear and contextual. It shall consider signal intensity, co-occurrence of distinct signal categories, component-level pattern density, repository-wide recurrence, and explicit House Style approval or mitigation.
- **[SCORE-010]** Each extracted Slop Signal shall have a stable identity within its reachable state and may contribute its base weight only once. Multiple Slop Patterns may cite the same signal without duplicating that base contribution.
- **[SCORE-011]** Additional score may come only from explicit, versioned, capped interaction terms representing meaningful co-occurrence, saturation, repetition, or composition. Every interaction contribution shall identify its participating signals and cap.
- **[SCORE-012]** Adding or reorganizing an explanatory rule shall not alter scores unless it introduces new evidence or an explicitly versioned interaction model.
- **[SCORE-013]** Repeating the same utility token or increasing component size shall not increase a score without bound. Component scoring shall emphasize the strongest meaningful pattern cluster plus bounded breadth of additional patterns.
- **[SCORE-014]** Repository scoring shall reflect prevalence and recurrence across components rather than the sum of component scores, so repository size alone does not determine the result.
- **[SCORE-015]** House Style Profile decisions shall have explicit, inspectable effects on contributions rather than hidden post-processing adjustments.
- **[SCORE-016]** House Style approval shall neutralize only the specifically matched contribution. It shall not create negative score credit or offset unrelated Slop Signals or interactions.
- **[SCORE-017]** Every mitigated contribution shall remain visible in report evidence with the matching House Style Profile entry and rationale.
- **[SCORE-018]** A Component Profile's intrinsic AI Slop Score shall use its highest-scoring compatible reachable-state family, breaking an exact score tie in favor of higher Finding Confidence and then the canonical state fingerprint. Materially different reachable states shall be listed with their own evidence, scores, and confidence rather than averaged together; enforcement eligibility shall still apply confidence policy independently.
- **[SCORE-019]** State-dependent scores shall identify their condition sets so a Design Authority can distinguish persistent, responsive, themed, and interaction-only presentations.
- **[SCORE-020]** Accessibility and semantic-HTML violations shall not contribute to the AI Slop Score. They represent distinct quality dimensions and belong to dedicated tools.
- **[SCORE-021]** The score shall estimate the strength and recurrence of configured Slop Patterns. It shall not be described as a probability, proof of AI authorship, or objective aesthetic grade.
- **[SCORE-022]** Thresholds and weights shall be configurable.
- **[SCORE-023]** Default thresholds shall be treated as starting policy, not mathematical proof.
- **[SCORE-024]** A score shall only be compared meaningfully when scanner version, configuration, and analysis coverage are compatible.
- **[SCORE-025]** V1 score comparisons shall be limited to components within one repository and scans of that repository using compatible policy. The product shall not rank unrelated repositories or imply that House Style-adjusted scores share a universal scale.
- **[SCORE-026]** The calibration corpus may support a portable default profile later, but it shall not make cross-repository rankings a V1 feature.
- **[SCORE-027]** Every displayed score shall include a named interpretation band and access to its raw rule contributions.
- **[SCORE-028]** Discovery report mockups shall use these provisional interpretation bands: `minimal` (0–19), `low` (20–39), `moderate` (40–59), `high` (60–79), and `dominant` (80–100).
- Band boundaries and the aggregation formula remain calibration questions until report mockups and Calibration Cases have been evaluated with intended users. Changing the provisional boundaries before implementation does not constitute a compatibility break.
- **[SCORE-029]** Every repository score shall be accompanied by multidimensional Analysis Coverage. Partial coverage shall be prominent and shall prevent the score from implying that unanalyzed code is clean.
- **[SCORE-030]** Every Finding shall include independent `high`, `medium`, or `low` confidence describing static-analysis certainty. Confidence shall not be derived from or folded into the AI Slop Score.
- **[SCORE-031]** Discovery and advisory reports shall show all confidence levels. Full V1 enforcement shall consider only high-confidence Findings by default; enforcing lower-confidence Findings shall require explicit policy.
- **[SCORE-032]** Findings shall have a Policy Disposition of `report`, `suppress`, or `enforce`, evaluated from explicit repository policy.
- **[SCORE-033]** The bot shall support advisory mode, where findings never fail the process.
- **[SCORE-034]** The bot shall support enforcement mode, where configured score-band, confidence, and disposition policy may produce a non-zero exit status.
- **[SCORE-035]** Enforcement shall be based on concrete new or materially worsened Findings that meet configured confidence and finding-score policy and have an `enforce` disposition. A repository AI Slop Score change alone shall never fail a build.

### 6.4 Units of analysis

- A statically represented UI element is the primary evidence location.
- A Finding is one Slop Pattern evaluated for one actionable owner in one compatible reachable-state family.
- A React component, represented by its Component Profile, is the primary refactoring and local score unit.
- A page is a contextual analysis boundary for composition rules such as Template Convergence; its route or page component remains the actionable owner and uses the same Component Profile model.
- A Repository Profile aggregates Component Profiles and repeated signals within one Analysis Scope to detect aesthetic convergence.
- **[MODEL-001]** An Analysis Scope is the outermost scoring boundary. Cross-scope summaries shall preserve the separate scores rather than produce a blended score.
- **[MODEL-002]** A repository-wide aggregate shall not erase component-level evidence or produce an unactionable universal quality grade.

## 7. Functional requirements

### FR-1: Repository discovery

**[DISCOVERY-001]** The bot shall accept a repository path, discover supported source files, honor standard ignore behavior where practical, and allow include/exclude overrides.

**[DISCOVERY-002]** Repository discovery shall resolve symbolic links safely. It may follow a link only when the resolved target remains within the configured repository root. It shall detect cycles, deduplicate files by resolved identity, and report skipped external links as coverage diagnostics.

**[DISCOVERY-003]** The scanner shall never traverse a symlink into a home directory, mounted secret, dependency cache, or any other target outside the repository boundary by default.

**[DISCOVERY-004]** The default maximum size for an individual supported source file shall be 2 MiB. A larger file shall be skipped with an explicit parse-coverage diagnostic unless configuration deliberately raises the limit for the relevant Analysis Scope.

**[DISCOVERY-005]** Skipped large, minified, or generated-looking files shall never count as clean. Diagnostics shall report their paths, sizes, skip reasons, and effect on coverage without embedding their contents.

**[DISCOVERY-006]** Discovery shall always exclude `.git` and scanner-generated report directories. It shall exclude dependency, vendor, generated, and build-output paths such as `node_modules`, `.next`, `dist`, `build`, and `coverage` by default and shall honor `.gitignore`.

**[DISCOVERY-007]** Configuration may explicitly include an otherwise ignored repository-internal path. It shall never include `.git` or a path resolving outside the repository boundary. Verbose discovery diagnostics shall identify the ignore or include rule responsible for a path decision.

**[DISCOVERY-008]** For a monorepository, configuration shall define one or more frontend Analysis Scopes. Each scope shall have independent file boundaries, House Style Profile, component scores, Repository Profile, Reviewed Baseline, and report section.

**[DISCOVERY-009]** Root configuration may supply inherited defaults, but workspace overrides shall be explicit and shall not leak into sibling scopes. The top-level report shall summarize scope results without calculating a blended monorepository AI Slop Score.

**[DISCOVERY-010]** House Style and rule policy precedence, from lowest to highest, shall be built-in defaults, repository-root profile, Analysis Scope profile, and narrow source Suppression.

**[DISCOVERY-011]** Configuration collections shall declare `extend` or `replace` behavior explicitly rather than relying on generic deep merging. `config validate --effective <scope>` shall print the resolved policy and provenance of each value for review and debugging.

### FR-1.1: Command-line interface

**[CLI-001]** The product shall ship one `ai-ui-slop` executable with these V1 commands:

- `init` discovers likely Analysis Scopes and creates a reviewable configuration draft;
- `scan` analyzes configured scopes and writes selected reports;
- `config validate` validates configuration and the House Style Profile and can print effective scoped policy;
- `baseline create` creates an unreviewed baseline candidate and semantic diff without enabling enforcement;
- `baseline accept` records explicit review metadata and promotes a candidate to the checked-in Reviewed Baseline;
- `baseline check` validates baseline format and matches it against the current scan;
- `explain <rule-id>` prints the rule's rationale, observable signals, counterexamples, remediation guidance, and references;
- `feedback bundle` creates a local, reviewable, redacted evaluation package for optional sharing;
- `update check` explicitly checks canonical release metadata without installing anything;
- `schema` prints or writes the configuration and report schemas matching the binary;
- `version` prints binary, schema, and rule-pack versions.

**[CLI-002]** Invoking `ai-ui-slop` without a subcommand shall behave like `ai-ui-slop scan`. Commands shall not prompt interactively in CI. Human diagnostics shall go to standard error when standard output is reserved for a requested machine-readable result.

**[CLI-003]** `init` shall:

- discover and present likely frontend Analysis Scopes;
- generate a commented `ai-ui-slop.config.jsonc` draft;
- suggest `.ai-ui-slop/reports/` for the repository's ignore file without modifying it unless explicitly requested;
- list unresolved workspace, routing, Tailwind, wrapper, and page-boundary assumptions;
- refuse to infer or approve a House Style Profile;
- refuse to overwrite existing configuration.

**[CLI-004]** All generated assumptions shall require visible Design Authority review before enforcement can be enabled.

### FR-1.1.1: First-run and enforcement lifecycle

**[ONBOARD-001]** The supported onboarding sequence shall be:

1. `init` creates an unapproved configuration draft and lists unresolved assumptions.
2. `config validate --effective <scope>` exposes every effective value, assumption, and provenance source.
3. The first `scan` for each Analysis Scope runs repository-wide in advisory mode and reports every Finding.
4. The Design Authority reviews Findings, House Style entries, narrow Suppressions, unresolved assumptions, and coverage.
5. The repository is cleaned incrementally from the Refactoring Brief and rescanned.
6. `baseline create` produces an unreviewed candidate containing only intentionally retained Findings.
7. `baseline accept` records review and binds the Reviewed Baseline to the exact effective-policy fingerprint.
8. Enforcement may then be enabled explicitly for that Analysis Scope.

**[ONBOARD-002]** Enforcement shall require an explicit policy switch, a compatible Reviewed Baseline whose policy fingerprint matches the current effective configuration, no unresolved generated assumptions, and satisfaction of every coverage floor required by the enforced rules. Requesting enforcement without these lifecycle prerequisites shall be invalid configuration and return exit code `2`; falling below coverage after valid enforcement begins shall return exit code `3`.

**[ONBOARD-003]** The GitHub Action shall default to advisory mode until the checked-in configuration explicitly enables enforcement and the checked-in Reviewed Baseline satisfies these prerequisites. No command or integration shall automatically approve generated assumptions, add a House Style entry or Suppression, create or accept a baseline, or reinterpret the initial repository state as clean.

**[ONBOARD-004]** Normal commands shall perform no update checks or other nonessential network requests. `update check` shall be the only V1 update-discovery command; it shall report available release metadata without downloading, installing, or changing the current binary.

**[ONBOARD-005]** Updates shall require an explicit external install step or a deliberate GitHub Action version-pin change. Offline behavior shall remain fully supported.

**[ONBOARD-006]** The CLI shall use this stable V1 exit-code contract:

- `0`: analysis completed and no enforceable regression exists; advisory Findings may exist;
- `1`: one or more enforceable new or materially worsened Findings exist;
- `2`: invocation or configuration is invalid;
- `3`: analysis coverage violates configured policy or required source could not be analyzed;
- `4`: the scanner encountered an internal failure.

**[ONBOARD-007]** Machine-readable output shall record the same outcome category. Documentation shall warn CI users not to collapse codes `2`–`4` into an ordinary policy failure.

### FR-1.2: Progress reporting

**[PROGRESS-001]** Interactive scans shall provide a concise progress display on standard error showing the current scan phase, completed and total work when known, elapsed time, and notable coverage problems. The display shall report actual analyzer work rather than generic activity messages.

**[PROGRESS-002]** At minimum, the progress model shall distinguish:

1. discovering analysis scopes and files;
2. parsing supported source;
3. resolving styles and component relationships;
4. discovering routes and classifying Page Archetypes;
5. evaluating Slop Patterns;
6. aggregating scores and work batches;
7. writing reports and validating artifacts.

**[PROGRESS-003]** The CLI shall support `--progress auto|always|never`, with `auto` as the default. Animated progress shall appear only on an interactive terminal in `auto` mode. Non-interactive and CI runs shall emit occasional plain phase summaries without cursor control or ANSI animation. Machine-readable standard output shall never contain progress rendering.

**[PROGRESS-004]** The default display shall show phase and aggregate counts rather than rapidly changing source paths. An explicit verbose mode may show the current path. Narrow terminals, terminals without color, redirected streams, and interrupted scans shall remain readable.

**[PROGRESS-005]** The default interactive presentation shall contain one stable overall progress bar and one current-phase status line. It shall not render separate animated bars for worker threads. The phase line shall show the phase name, completed and total work when known, elapsed time or rate where useful, and unresolved-item counts when they become available.

**[PROGRESS-006]** Current filenames and worker-level details shall appear only in explicit verbose mode. Verbose activity shall remain on standard error and shall not alter analysis behavior.

**[PROGRESS-007]** During repository discovery, the display shall use an indeterminate state until scopes, files, and measurable work units are known. It shall not estimate progress from elapsed time.

**[PROGRESS-008]** After discovery, the overall bar shall use benchmark-derived work-unit weights for parsing, resolution, graph construction, rule evaluation, aggregation, and report writing. Reported progress shall be monotonic. Weight definitions shall be versioned with the scanner and included in progress-trial evidence when they change materially.

**[PROGRESS-009]** Before the final CLI presentation is selected, requirements discovery shall include a progress-display trial against small, large, partially analyzable, and failing scans. The Design Authority shall evaluate whether the display answers both “how far along is the scan?” and “what is the scanner doing?” without excessive motion or noise.

**[PROGRESS-010]** The trial shall measure rendering overhead with at least 20 alternating progress-on/progress-off cold pairs on the pinned reference runner. Median paired overhead must stay at or below 2%; the evidence shall also publish the paired distribution and 95% confidence interval. Progress shall use a bounded refresh rate and shall not affect report bytes, scores, Finding order, or exit status.

**[PROGRESS-011]** On the first interrupt signal, the scanner shall stop scheduling new work and perform only safe shutdown. It shall restore the terminal, emit a concise cancellation summary, remove temporary artifacts, and exit `130` without writing a canonical report or baseline. A second interrupt may terminate immediately.

### FR-1.3: Resource budgets

**[RESOURCE-001]** Every scan invocation and Analysis Scope shall be evaluated under explicit resource budgets. Per-scope V1 defaults shall be:

- no more than 20,000 eligible source files;
- no more than 512 MiB of total eligible source bytes;
- no more than 2 MiB for one eligible source file, as defined by repository discovery;
- no more than 2,000,000 AST nodes for one source file;
- no more than 256 compatible reachable-state families for one component;
- no more than 1,000 emitted diagnostics for one stable reason code, followed by one counted truncation record;
- no more than 2 MiB for any one auxiliary manifest, lockfile, TypeScript, Tailwind, or CSS configuration input;
- no more than 64 MiB of auxiliary configuration and imported CSS bytes;
- no more than 2,000,000 recorded component, import, route, and ownership graph edges;
- no more than 128 traversed directory levels and 64 static configuration-import levels.

**[RESOURCE-009]** Scan-global V1 defaults shall admit no more than 64 Analysis Scopes, 20,000 unique eligible files, 512 MiB of unique eligible source bytes, 64 MiB of auxiliary configuration and imported CSS bytes, 4,096 static configuration-import edges, 2,000,000 total component/import/route/ownership graph edges, 10,000 emitted diagnostics across all reason codes before counted truncation summaries, 1 GiB of allocator-accounted live analysis data, 256 MiB of canonical JSON, and 64 MiB of generated Markdown. Accounted data shall include parser arenas, owned intermediate representations, graphs, evidence, and serialization buffers. A resolved file shared by scopes shall count once toward global discovery bytes but every scope-specific analysis result shall remain independent.

**[RESOURCE-010]** Memory evidence shall report both allocator-accounted peak live analysis bytes and operating-system peak RSS or working set. The GitHub Action shall apply an outer process-memory ceiling of 1.5 GiB through an available runner isolation mechanism in addition to the 1 GiB internal admission budget. Local platforms shall enforce the internal budget consistently and report OS peak memory; inability to install an equivalent outer local limit shall be documented in the support matrix rather than described as full process containment.

**[RESOURCE-002]** Local wall time shall be unlimited by default but configurable. The GitHub Action shall apply a configurable wall-time budget of 10 minutes by default, independent of the workflow job's outer timeout.

**[RESOURCE-003]** When a resource budget is exhausted, the scanner shall stop scheduling work for only the affected Analysis Scope or analysis stage where safe isolation is possible. It shall record the budget identifier, configured limit, observed amount, affected scope or constructs, and resulting Analysis Coverage loss, then return exit code `3`. It shall not guess missing results, treat skipped work as clean, or convert deterministic resource exhaustion into exit code `4`.

**[RESOURCE-004]** A trusted operator may raise ordinary operational limits deliberately through CLI or workflow inputs, while repository policy may only lower them. Pull-request-controlled configuration shall never raise the trusted scan-global ceiling. No configuration shall disable checked arithmetic, repository and symlink boundaries, recursion-depth guards, diagnostic truncation records, output-size protections, or other structural denial-of-service defenses.

**[RESOURCE-005]** Canonical artifacts shall use atomic generation. A budget-limited scan may produce a complete, schema-valid report whose scope status is `incomplete`, but it shall never leave a partially serialized JSON, Markdown, or baseline file. If the canonical-output budget itself is exhausted, no replacement artifact shall be committed and diagnostics shall describe the failure.

**[RESOURCE-006]** Canonical artifacts shall use atomic writes so cancellation or failure cannot leave a partial file that appears complete.

**[RESOURCE-007]** `scan` may automatically replace only output files carrying valid AI UI Slop Bot generated-artifact metadata of the expected artifact type at the expected report paths. It shall always refuse to overwrite an unrelated existing file; `--force` shall not bypass artifact identity or filesystem-object safety.

**[RESOURCE-008]** `baseline create` shall refuse to replace an existing baseline by default. Replacement shall require `--force` and shall print or write a change summary covering added, removed, worsened, improved, and ambiguously matched baseline entries before committing the atomic replacement.

### FR-1.4: Source and artifact mutation boundary

**[ARTIFACT-001]** The scanner shall describe normal analysis as **source-non-mutating**, not read-only. It shall never modify target source, pre-existing target-project configuration, dependency manifests or lockfiles, installed dependencies, Git metadata, or application state. Explicit commands may create documented scanner-owned configuration drafts, reports, feedback bundles, schemas, and baseline artifacts, but shall not overwrite an existing scanner configuration draft.

**[ARTIFACT-002]** Every output path shall resolve within the configured repository boundary and shall be either a documented default or an explicit user selection. Artifact operations shall refuse symlink targets, multiply hard-linked targets, directories, devices, sockets, and other special files. Safe-open and replacement logic shall avoid following links and shall revalidate the destination during commit to resist path-swap races.

**[ARTIFACT-003]** Generated replacement shall use a temporary file in the destination directory, restrictive creation permissions, complete serialization and schema validation, flush where supported, and one atomic rename. Temporary files shall be removed on ordinary failure or cancellation. An existing artifact may be replaced only when its validated type marker matches the command's expected artifact type; an unrelated file shall never be replaced by `--force`.

### FR-2: Static parsing

**[PARSE-001]** The bot shall parse supported React source with a TypeScript-aware AST. A syntax error in one file shall produce a diagnostic without aborting analysis of unrelated files.

**[PARSE-002]** JSX parsing shall be enabled according to extension, syntax, and explicit configuration rather than assuming every TypeScript file permits JSX. V1 shall also recognize statically analyzable `React.createElement` calls and automatic JSX-runtime element calls as UI structure, while treating source JSX as the primary analysis path.

**[PARSE-003]** Supported source shall be UTF-8 with or without a byte-order mark. Invalid UTF-8 shall produce a parse-coverage failure; the scanner shall not replace invalid bytes or guess another encoding.

**[PARSE-004]** Line-ending differences shall not change semantic fingerprints or rule evidence. Location calculation shall remain correct for LF and CRLF input.

**[PARSE-005]** For V1, the bot shall extract Tailwind signals from literal `className` values and the explicitly supported statically resolvable class-composition forms. It shall identify unsupported dynamic styling as incomplete coverage.

**[PARSE-006]** The V1 static-resolution surface shall include:

- literal `className` strings;
- statically known portions of template literals;
- conditional and logical branches with finite class values;
- common `clsx`, `classnames`, `cn`, and `tailwind-merge` call patterns;
- CVA variant definitions and statically selected variant values;
- repository-configured aliases for local class-composition wrappers.

**[PARSE-007]** The scanner shall preserve branch and variant context where it affects whether signals can co-occur. It shall not combine mutually exclusive classes into a pattern that cannot exist at runtime.

**[PARSE-008]** Parsing and static resolution shall operate without executing project code. When a result would require execution, the scanner shall report the affected analysis capability and coverage loss.

### FR-3: Component and element analysis

**[ANALYSIS-001]** The bot shall associate evidence with the narrowest useful source unit, normally a JSX element, and issue the corresponding Finding against its owning component.

**[ANALYSIS-002]** The bot shall also produce a Repository Profile that groups recurring Slop Patterns across components. The profile shall make repeated patterns visible while preserving links to every actionable component Finding.

**[ANALYSIS-003]** When multiple usage sites inherit the same detected pattern from a shared primitive, the scanner shall issue one actionable Finding at the primitive definition and list usage sites as impact evidence. It shall not duplicate the inherited Finding at every call site.

**[ANALYSIS-004]** Approval of a primitive in the House Style Profile shall suppress or mitigate the primitive's own configured contribution. It shall not grant blanket immunity to excessive, contextually inappropriate, or independently styled usage sites.

**[ANALYSIS-005]** Adapters may understand well-known component libraries to classify roles and trace styling through shared primitives. Findings shall cite observable styling or composition evidence, not the library name. Use of shadcn/ui or any other popular library shall never be a violation by itself.

**[ANALYSIS-006]** Cross-file resolution shall statically interpret repository-local `tsconfig.json` and `jsconfig.json` configuration, including applicable `extends`, `baseUrl`, and `paths` behavior, without invoking TypeScript or executing configuration. It shall resolve relative imports, configured aliases, and workspace-local package exports within the repository boundary.

**[ANALYSIS-007]** V1 shall resolve named and wildcard re-exports, index/barrel modules, static-string dynamic imports, `React.lazy` imports with static targets, and supported lazy route declarations with statically known module paths.

**[ANALYSIS-008]** Graph traversal shall be cycle-safe. Runtime-computed module targets shall remain unresolved and shall reduce graph coverage; the scanner shall not infer a likely target from naming or directory proximity.

**[ANALYSIS-009]** The component model shall recognize function components wrapped in standard `memo`, `forwardRef`, and nested combinations of those wrappers. Configuration may declare repository-local transparent wrapper aliases when the wrapped component remains statically identifiable.

**[ANALYSIS-010]** The component model shall recognize class components extending `React.Component`, `React.PureComponent`, or statically resolved imported aliases and shall analyze JSX returned from `render()` as an ordinary component Finding unit.

**[ANALYSIS-011]** Arbitrary higher-order components that transform rendering or obscure the wrapped component shall produce reduced graph confidence unless a versioned adapter understands their semantics.

**[ANALYSIS-012]** Historical decorators, mixins, or dynamic inheritance that obscure render ownership shall reduce graph coverage unless a versioned adapter understands them.

**[ANALYSIS-013]** Configuration inherited from an unavailable dependency or external path shall not be fetched or executed. Unresolved and cyclic graph edges shall produce traceable graph-coverage diagnostics while allowing unrelated components to be analyzed.

### FR-3.1: Page discovery

**[ROUTE-001]** V1 shall discover page and route boundaries through adapters for:

- Next.js `app` routing;
- Next.js `pages` routing;
- common statically declared React Router routes.

**[ROUTE-002]** Repository configuration shall allow maintainers to declare custom page components, route roots, and adapter overrides. Directory names or naming conventions alone shall not silently determine scoring.

**[ROUTE-003]** Configuration may assign one or more Page Archetypes, or `custom`, to a route or page component. Reports shall distinguish configured classification from inferred classification and shall expose inference confidence and evidence.

**[ROUTE-004]** Configured classification controls which archetype-specific structural signatures are evaluated. It shall not suppress generic decoration, repetition, container, token, or rhythm rules.

**[ROUTE-005]** The scanner shall expose discovered page boundaries, their discovery source, and unresolved route composition in coverage output. Maintainers shall be able to correct an inferred boundary without modifying application source.

### FR-3.2: Structural use of visible text

Bot 2 may inspect visible text only to classify UI roles needed by structural rules, such as an eyebrow label, heading, call to action, badge, or feature-card description.

**[TEXT-001]** It shall not score wording, vocabulary, punctuation, tone, AI-like phrasing, or prose quality. Text used as structural evidence shall be minimized in output and identified as role-classification evidence. Ambiguous roles shall lower confidence or remain unclassified rather than trigger prose heuristics.

### FR-4: Explainable evaluation

**[EXPLAIN-001]** Each finding shall identify:

- the rule or rule combination that triggered;
- the source location;
- the relevant source evidence;
- each score contribution, when scoring is used;
- why the combination merits review;
- a remediation direction that preserves behavior and does not prescribe an unrelated visual style.

**[EXPLAIN-002]** Remediation directions shall express preservation as an obligation, not as a scanner guarantee that a proposed or completed change is behaviorally equivalent.

### FR-5: Configuration

**[CONFIG-001]** Repository configuration shall allow users to:

- enable or disable rules;
- change weights, thresholds, confidence requirements, and Policy Dispositions;
- ignore paths;
- declare allowed utilities, patterns, or design tokens;
- select advisory or enforcement behavior;
- choose output formats.

**[CONFIG-002]** Configuration errors shall fail clearly rather than falling back silently.

**[CONFIG-003]** The canonical V1 configuration file shall be `ai-ui-slop.config.jsonc`. The project shall publish a versioned JSON Schema for validation, editor completion, documentation, and migration tooling.

**[CONFIG-004]** Configuration shall be declarative and shall not execute repository code. Unknown fields, incompatible schema versions, invalid rule identifiers, and invalid values shall produce actionable errors. A machine-readable validation result shall be available to CI and downstream tooling.

**[CONFIG-005]** The configuration shall contain an explicit **House Style Profile** capable of declaring:

- approved design tokens and Tailwind theme values;
- approved shared primitives and reference components;
- intentional exceptions with rationale;
- unwanted combinations expressible through parameters exposed by built-in rules;
- rule overrides that are visibly distinct from universal defaults.

**[CONFIG-006]** The House Style Profile may include human-readable intent, brand guidance, examples, and remediation notes for Refactoring Briefs. Free-form prose shall never directly affect extraction, rule matching, confidence, or scoring.

Only schema-defined structured tokens, component and variant references, rule parameters, archetype settings, capability mappings, and explicit exceptions may alter deterministic analysis.

**[CONFIG-007]** V1 Page Archetype extensions shall use a narrow declarative schema. A repository may assign a stable custom archetype identifier and human-readable description, then classify it using only versioned structural-signal identifiers supplied by the scanner. Its definition may specify required, supporting, and excluding signals plus bounded thresholds permitted by the Template Convergence Rule Contract.

**[CONFIG-008]** A custom Page Archetype shall affect only page classification and Template Convergence context. It shall not define a new extractor, Slop Signal category, Slop Pattern, score formula, arbitrary expression, or executable behavior. Unsupported signal identifiers or parameters shall be configuration errors rather than ignored input.

**[CONFIG-009]** Canonical reports shall embed each normalized effective custom-archetype definition, its provenance, schema version, and deterministic fingerprint. Baseline compatibility shall include that fingerprint. Pages matching neither a built-in nor custom definition shall remain `unknown` and receive generic non-archetype analysis.

**[CONFIG-010]** Approved reference components shall be identified by normalized repository-relative module path and exported symbol, using `default` for a default export. Configuration may assign a stable human-facing alias, but line numbers and inferred display names shall not determine identity.

**[CONFIG-011]** A missing, renamed, ambiguous, or changed export shall produce a configuration error requiring Design Authority review. The scanner shall not silently rematch an approved reference to another component with a similar name.

**[CONFIG-012]** Reference-component approval shall distinguish base styling, named CVA or prop variants, specific variant combinations, and optional usage-context constraints. Approval of a component shall not automatically approve every variant or call site.

**[CONFIG-013]** Unspecified, unresolved, or runtime-computed variants shall retain normal signal evaluation and Finding Confidence behavior.

**[CONFIG-014]** The scanner shall not silently infer the House Style Profile from dominant repository patterns. A future inference feature may propose a profile, but the Design Authority must review and accept each proposal before it affects Findings or scores.

**[CONFIG-015]** The Validated MVP House Style Profile shall support exactly the two MVP rule identifiers and their exposed thresholds, approved design-token values, approved shared primitives by normalized module and export, ignored paths, and narrow Suppressions with owner and rationale. Profile inheritance, custom Page Archetypes, capability mappings, enforcement dispositions, and cross-scope overrides are Full V1 capabilities.

### FR-5.1: Rule distribution

**[RULEPACK-001]** V1 rules shall be built into and versioned with the scanner binary. Configuration may enable, disable, or tune exposed rule parameters but shall not load or execute repository-supplied rule code.

**[RULEPACK-002]** If ADR 0003 accepts the Rust/Oxc core, the built-in rule pack shall use this typed hybrid implementation:

- Rust code owns extraction, symbolic reachability, graphs, static resolution, scoring mechanics, and complex predicates;
- embedded schema-validated data owns calibrated signal weights, caps, provisional bands, Page Archetype signatures, explanations, references, and counterexample metadata;
- code and embedded data are compiled into the same signed binary and share one rule-pack version.

**[RULEPACK-005]** If the feasibility benchmark rejects Rust/Oxc, ADRs 0003 and 0004 and this implementation allocation shall reopen together; the replacement shall preserve one typed mechanics layer, schema-validated calibration data, and a single versioned rule-pack artifact without requiring Rust specifically.

**[RULEPACK-003]** V1 shall not create a general-purpose rule language or external executable DSL. The constrained custom-Page-Archetype schema belongs to the built-in mechanics; it composes only built-in structural signals within Template Convergence. Embedded data and normalized custom definitions shall be reviewable and testable without allowing arbitrary repository behavior.

**[RULEPACK-004]** Third-party executable plugins are outside V1. A future release may consider declarative, data-only rule packs only after defining schemas, provenance, compatibility, conflict handling, and score reproducibility. Reports shall identify the exact built-in rule-pack version.

### FR-6: Suppression

**[SUPPRESS-001]** Users shall be able to suppress a false positive at a narrow scope. Each Suppression shall identify the rule, include a reason and owner, and may include an expiry date.

**[SUPPRESS-002]** Reusable intentional patterns shall be approved through the House Style Profile rather than repeated source suppressions. Broad file-wide or repository-wide exceptions shall require explicit configuration and shall not be expressible as an incidental inline comment.

**[SUPPRESS-003]** Active Suppressions shall remain visible in output. Expired, unmatched, and no-longer-needed Suppressions shall be reported so exceptions do not become invisible or permanent by accident.

### FR-7: Human-readable output

**[TERMINAL-001]** Terminal output shall be concise, grouped predictably, and include file paths and line/column locations. Color shall be optional and disabled automatically when inappropriate.

**[TERMINAL-002]** All repository-derived paths, owner and component names, source tokens, diagnostics, configuration prose, and evidence shall be treated as hostile presentation data. Terminal rendering shall visibly escape C0 and C1 controls, ANSI escape sequences, bidirectional-control characters, and embedded line breaks rather than allowing them to alter cursor position, direction, color, or diagnostic boundaries.

**[TERMINAL-003]** Terminal hyperlinks derived from source or configuration shall be disabled by default and enabled only by an explicit option. When enabled, their target and visible label shall be independently validated and escaped.

### FR-8: Agent-readable output

**[REPORT-001]** Versioned JSON shall be the canonical machine-readable contract. The bot shall also generate a Markdown Refactoring Brief from the same analysis model.

**[REPORT-002]** Default artifact locations shall be:

- `.ai-ui-slop/reports/report.json` for canonical scan results;
- `.ai-ui-slop/reports/refactoring-brief.md` for the generated handoff;
- `ai-ui-slop.baseline.json` at the repository root when a baseline is explicitly created;
- `ai-ui-slop.config.jsonc` at the repository root for configuration.

The reports directory should normally be excluded from version control. Configuration and a Reviewed Baseline are intended to be committed. CLI options may override report and baseline paths.

**[REPORT-004]** The report envelope shall contain tool, schema, rule-pack, policy, and semantic invocation metadata followed by an array of independent Analysis Scope reports. Each scope report shall contain its effective policy fingerprint, normalized custom-archetype definitions, complete coverage vector, Component Profiles, Findings, Repository Profile, baseline comparison, diagnostics, and Refactoring Brief batches.

**[REPORT-005]** The top-level summary shall contain only cross-scope counts, outcome status, and per-scope statuses. It shall not contain or imply a blended AI Slop Score, Analysis Coverage ratio, House Style Profile, or baseline result.

**[REPORT-006]** Canonical arrays shall use documented deterministic ordering. Unless a narrower schema rule applies, scope reports shall sort by stable scope identifier, Component Profiles by normalized path and exported owner symbol, Findings by normalized path, owner symbol, rule identifier, reachable-state fingerprint, and Finding fingerprint, and work batches by dependency order followed by stable batch identifier.

**[REPORT-007]** Schema-defined fields shall not disappear merely because a concept is unavailable. The schema shall use explicit `null`, empty collections, or typed status objects such as `not_applicable`, `not_requested`, `incomplete`, and `failed`, as appropriate. It shall distinguish no Findings from incomplete analysis and fatal scanner failure.

**[REPORT-008]** Terminal output, Markdown Refactoring Briefs, GitHub summaries, and future presentation adapters shall be projections of the validated canonical report model and shall not maintain independent semantic result models. Volatile execution details such as elapsed time, wall-clock timestamps, terminal width, worker count, and host identity shall remain outside the canonical report artifact; an explicitly requested non-reproducible diagnostics artifact may carry them separately.

**[REPORT-009]** JSON output shall rely on standards-compliant string serialization without interpolating repository data into raw JSON fragments. Markdown generation shall emit no repository-derived raw HTML, shall choose or escape code fences so evidence cannot terminate them, and shall sanitize link destinations and table delimiters. GitHub summaries shall apply the same hostile-data policy.

**[REPORT-010]** Source ranges shall include zero-based UTF-8 byte offsets and one-based human-facing line and Unicode-scalar column numbers. The schema shall define these conventions explicitly. Platform adapters may translate columns for their target APIs, but displayed locations shall not participate in Finding fingerprints.

**[REPORT-011]** No output shall render the AI Slop Score with a percent sign or describe it as the likelihood that AI authored the source.

**[REPORT-012]** By default, reports shall include source paths, ranges, component and structural-role names, and normalized semantic rule evidence. Exact class tokens may be included only when they contain no visible-copy payload, URL or data payload, control characters, or secret-like value; otherwise reports shall emit a redacted semantic category and a domain-separated digest of the normalized redacted representation sufficient for matching. Public reports shall never hash the raw sensitive payload or a reversible encoding of it. They shall not embed full components or user-facing copy.

**[REPORT-013]** All canonical paths shall be relative to the configured repository or Analysis Scope root, normalized with `/`, and stable across supported operating systems. Reports, baselines, feedback bundles, and Finding fingerprints shall not contain absolute checkout paths, usernames, or home-directory locations.

**[REPORT-014]** Analysis Scope identifiers shall use stable configured names rather than filesystem paths.

**[REPORT-015]** Canonical paths shall preserve repository spelling and shall not be globally lowercased. Discovery shall detect paths that collide under case-insensitive filesystem semantics and fail with exit code `3`, identifying the collisions. Finding fingerprints shall not be generated from ambiguous paths.

**[REPORT-016]** An explicit option may include short source excerpts when required by a downstream workflow. Reports shall identify when excerpts are enabled. Full-file embedding is outside the V1 report contract.

### FR-8.1: Feedback and telemetry

**[PRIVACY-001]** V1 shall collect and transmit no automatic usage, performance, repository, Finding, or satisfaction telemetry.

**[PRIVACY-002]** `feedback bundle` shall create a local package containing only explicitly documented categories such as scanner/schema/rule-pack versions, policy metadata, benchmark measurements, redacted structural statistics, and user-supplied accepted/rejected/ambiguous labels. It shall exclude source code, visible product copy, secrets, raw repository paths, and remote repository identifiers by default.

**[PRIVACY-003]** The command shall show a human-readable manifest of every included file and data category before the user chooses whether to share it. Creating a bundle shall never upload it.

**[PRIVACY-004]** The schema shall support work batches that group related Findings. Each batch shall include:

- its priority and ordering dependencies;
- affected files and components;
- contributing Slop Patterns and source evidence;
- expected effect on component and repository scores;
- applicable House Style constraints and reference components;
- Preservation Obligations for behavior and accessibility, each labeled `observed`, `configured`, or `unknown` and linked to its evidence or rationale;
- suggested remediation direction;
- decisions intentionally left to the coding agent;
- vendor-neutral Capability Requirements for specialized design help;
- verification steps and acceptance conditions.

Preservation Obligations may cover observable component APIs, element roles, accessible names and relationships, form behavior, event-handler attachment, navigation targets, reachable state branches, responsive behavior, and project-specific constraints supplied by configuration. `observed` means the scanner found static source evidence, `configured` means the Design Authority supplied the constraint, and `unknown` means static analysis could not establish the relevant contract.

**[PRIVACY-005]** Verification steps may identify relevant existing tests, build, type-check, lint, accessibility, and visual-review procedures from static repository metadata or explicit configuration. The scanner shall not execute those procedures, claim that naming them proves success, or equate a lower AI Slop Score with behavior preservation. Unknown obligations shall require explicit human or downstream-agent review.

**[PRIVACY-006]** The Markdown Refactoring Brief shall render those batches for direct use by a coding agent and human reviewer. JSON and Markdown must agree, and both shall identify their scanner, policy, and schema versions.

**[PRIVACY-007]** The House Style Profile may map Capability Requirements to locally installed agent skills or workflows. The canonical report schema shall not require or hard-code a particular agent vendor, plugin, or skill name.

### FR-9: Determinism

**[DETERMINISM-001]** Given the same source, configuration, and scanner version, the bot shall produce equivalent findings and exit status.

**[DETERMINISM-002]** Each Finding shall have a stable identity fingerprint derived from Analysis Scope identifier, rule identifier, normalized module and export owner, the Rule Contract's versioned semantic occurrence key, and compatible reachable-state family. By default, all matching evidence for one rule, owner, and state family shall aggregate into one Finding. A rule that permits several Findings for that tuple shall define a normalized semantic occurrence key and collision tie-breaker, with collision fixtures. Fingerprints shall exclude line and column numbers, messages, score and band, raw utility ordering, evidence weights, and other presentation data. Normal source movement shall preserve identity where practical.

**[DETERMINISM-003]** Each Finding shall separately expose an evidence digest derived from its normalized Slop Signals and interactions. Evidence may therefore change without destroying Finding identity. Fingerprint and evidence-digest algorithms shall be versioned independently where compatibility requires it.

**[DETERMINISM-004]** V1 shall not use a persistent analysis cache. It may use bounded parallelism and in-memory indexes during one scan, but a clean uncached scan shall remain the performance and correctness reference.

**[DETERMINISM-005]** The default worker count shall be derived from available CPUs and constrained by the memory budget. The CLI shall provide `--jobs <n>`, including `--jobs 1` for deterministic debugging.

**[DETERMINISM-006]** Parallel scheduling shall not affect Finding order, scores, confidence, fingerprints, or report bytes. All observable results shall be canonically ordered before serialization.

**[DETERMINISM-007]** A future persistent cache shall require content-addressed inputs, explicit scanner and policy compatibility, safe invalidation, corruption recovery, and proof of customer-visible benefit before adoption.

### FR-9.1: Version compatibility

**[COMPAT-001]** The scanner binary, configuration/report schemas, and built-in rule pack shall have independently visible versions. Every canonical report and baseline shall record all applicable versions and a policy fingerprint.

**[COMPAT-002]** The scanner shall use Semantic Versioning. Before `1.0`, breaking CLI, configuration, report, baseline, or behavior contracts may occur only in minor releases. Patch releases may correct defects but shall not intentionally recalibrate scores, weights, bands, or policy defaults.

**[COMPAT-003]** Each pre-1.0 minor release shall provide migration support from the immediately preceding minor release. After `1.0`, ordinary Semantic Versioning compatibility applies.

**[COMPAT-004]** A rule, weight, normalization, band, or fingerprinting change may alter scores or baseline matches without changing the public schema. Baseline checks shall refuse silent comparison when rule-pack or fingerprint compatibility is not guaranteed.

**[COMPAT-005]** The CLI shall provide an explicit migration preview showing added, removed, changed, worsened, improved, and ambiguously matched Findings before updating an incompatible baseline. Migration shall never imply that newly unreported debt was fixed.

**[COMPAT-006]** CI examples shall pin an exact scanner version. Upgrading shall require reviewing the semantic report diff and any baseline migration preview before changing the pin.

**[COMPAT-007]** Every release shall publish a versioned support matrix naming tested Tailwind semantic-version ranges and configuration grammar snapshots, Rust target triples, libc or ABI choices, minimum operating-system versions, archive formats, and CPU feature baselines. Inputs or platforms outside that matrix shall be unsupported rather than implicitly covered by the labels “Tailwind v3/v4,” Linux, macOS, or Windows.

### FR-10: Agent handoff

**[HANDOFF-001]** The Validated MVP shall produce a repository-wide handoff that a coding agent can execute incrementally. The handoff shall prioritize Findings, preserve enough component context to plan related edits, identify constraints that must survive the refactor, and avoid prescribing changes unsupported by the evidence.

**[HANDOFF-002]** The handoff is the primary V1 delivery surface. It shall be usable without GitHub integration.

**[HANDOFF-003]** The handoff shall consist of canonical versioned JSON and its generated Markdown Refactoring Brief. The scanner shall not generate or apply source patches in V1.

**[HANDOFF-004]** Every work batch shall state that application behavior and accessibility semantics must be preserved or improved and that the scanner has not verified runtime equivalence. If external accessibility results are linked in a future release, they shall remain a separate dimension and shall not be folded into the AI Slop Score.

### FR-11: CI operation

**[CI-001]** The command-line interface shall run non-interactively in GitHub Actions and other CI systems. GitHub-specific annotations or pull-request comments may be added after the local scanner contract is stable.

Changed-code-only enforcement and presentation are post-V1 capabilities, after the rules have been calibrated on representative existing repositories. Full V1 may enforce whole-repository regressions against a Reviewed Baseline.

**[CI-002]** The first GitHub integration shall be a GitHub Action that:

- runs the same scanner used locally;
- uploads the canonical JSON and Markdown Refactoring Brief as workflow artifacts;
- writes a concise job summary containing status, per-scope Repository Profile scores, per-scope Analysis Coverage status, Finding counts, and artifact links;
- avoids inline review comments and annotations during repository-wide discovery scans.

**[CI-003]** The Action shall require only read access to repository contents and ordinary workflow metadata. It shall not require write access to code, pull requests, reviews, issues, checks, deployments, or other repository state.

**[CI-004]** Forked pull-request scans shall work without repository secrets. Missing optional permissions shall degrade only the affected presentation feature and shall not change scanner results.

**[CI-005]** The documented pull-request workflow shall use the `pull_request` event and analyze the pull-request revision with read-only permissions. V1 documentation and templates shall not use `pull_request_target` to process contributor-controlled source.

**[CI-007]** Pull-request enforcement shall evaluate contributor-controlled source against every enforcement-affecting input from the trusted target-branch revision or equivalently protected workflow inputs. Trusted Policy shall include scanner and rule-pack pins, scope assignment, include/exclude and ignore policy including `.gitignore`, House Style Profile, Suppressions, Reviewed Baseline, confidence and score thresholds, Policy Dispositions, resource ceilings, and custom Page Archetypes. Changes to those inputs in the pull request shall be reported for review but shall not weaken or redefine that pull request's enforcement result. New source Suppressions shall not take effect during the pull request that introduces them. If Trusted Policy cannot be obtained or verified, the Action shall fail closed with exit code `2` rather than using pull-request-controlled enforcement policy.

**[CI-008]** Every supported source file in a pull-request revision shall either belong to a scope defined by Trusted Policy or be reported as unassigned coverage loss. Silent exclusion of a new frontend workspace, supported file, or path through contributor-controlled policy is forbidden. An enforcement scan with unassigned supported source shall return exit code `3` until trusted scope or ignore policy is updated.

**[CI-006]** Full V1 shall enforce new or materially worsened Findings against a Reviewed Baseline when enforcement is enabled. A post-V1 release may present those regressions as inline annotations. V1 shall not require a separately hosted GitHub App.

### FR-11.1: Distribution

**[DIST-001]** Canonical V1 releases shall publish versioned native binaries and checksums through GitHub Releases. The composite GitHub Action shall invoke a pinned released scanner version rather than building the scanner or target repository during the workflow.

**[DIST-002]** Every release binary shall have a published SHA-256 checksum, GitHub build-provenance attestation, and associated software bill of materials. Release documentation shall describe verification, including optional provenance verification with the GitHub CLI.

**[DIST-003]** The composite Action shall verify the selected binary against an authenticated asset manifest embedded in or cryptographically bound to the immutable pinned Action revision, and shall fail closed on missing, mismatched, or unverifiable integrity data. A checksum downloaded only beside a binary from the same mutable location shall not establish trust.

**[DIST-005]** Canonical release assets and their manifest shall be published through immutable releases. Release workflows and documentation examples shall pin third-party Actions by full commit SHA, bind provenance and SBOM subjects to the exact distributed archives and binaries, and document the trust bootstrap used by local verification.

**[DIST-006]** The Validated MVP Linux binary shall be published as an immutable asset with an authenticated digest manifest whose trust anchor is independent of the downloaded asset location. MVP documentation shall make successful manifest verification a prerequisite to execution; an adjacent checksum from the same mutable location shall not satisfy MVP integrity acceptance.

The Rust crate may support `cargo install` for contributors and users with a Rust toolchain. npm, Homebrew, Chocolatey, AUR, and other package-manager channels are deferred until customer demand justifies their ongoing release maintenance.

**[DIST-004]** An installer script shall not be published until its download source, version pinning, checksum or signature verification, failure behavior, and update behavior have been designed and tested.

### FR-12: Baseline adoption

**[BASELINE-001]** V1 shall report all Findings during the initial repository cleanup; it shall not silently create or apply a baseline.

**[BASELINE-002]** After the initial cleanup pass, the Design Authority may create a candidate baseline of remaining Findings. Candidate creation shall display and persist a semantic diff but shall not make the candidate Reviewed or enable enforcement.

**[BASELINE-003]** Promotion to a checked-in Reviewed Baseline shall require the explicit `baseline accept` command. Acceptance shall record the Analysis Scope, scanner version, schema version, rule-pack version, Finding Fingerprint algorithm version, Evidence Digest algorithm version, policy fingerprint, source revision when available, an approver label, acceptance timestamp, and rationale. These fields are audit metadata, not proof of the approver's external identity.

**[BASELINE-004]** Baseline acceptance shall also constitute Design Authority approval of the exact effective-policy fingerprint recorded in that candidate for the purpose of enabling enforcement. Any subsequent effective-policy change that affects analysis or enforcement shall require a new semantic preview and baseline review.

**[BASELINE-005]** The Reviewed Baseline shall retain each Finding's identity fingerprint, evidence digest, normalized evidence, score, band, confidence, and rationale and shall remain visible in reports.

**[BASELINE-006]** Full V1 enforcement shall fail on new Findings and materially worsened baseline Findings according to configured policy. It shall not require all accepted historical debt to be fixed at once. A resolved baseline entry shall remain in the accepted file until `baseline create` proposes its removal in a new candidate, the semantic preview identifies it, and `baseline accept` explicitly commits the revised baseline. A Finding whose accepted resolved fingerprint later resurfaces shall count as new.

A matched Finding is **materially worsened** when at least one of these occurs under compatible scanner, rule-pack, fingerprint, and policy versions:

- its AI Slop Score enters a higher interpretation band;
- its AI Slop Score increases by at least 10 points; or
- its evidence digest gains a new enforcement-relevant signal interaction that its Rule Contract explicitly designates as material.

**[BASELINE-007]** A confidence change alone shall not constitute worsening. Configuration, policy, default-weight, band, Rule Contract, or fingerprint-algorithm changes that can alter matching or enforcement shall require a migration preview and explicit baseline review rather than being presented as source regressions.

**[BASELINE-008]** The Repository Profile and its AI Slop Score shall support trend reporting and prioritization only. They shall not act as an opaque CI gate.

**[BASELINE-009]** Baseline matching shall use Finding identity fingerprints and tolerate ordinary line movement. Exact, resolved, stale, ambiguous, and unmatched states shall be reported explicitly. Ambiguous matches shall never be treated as enforceable regressions; an enforcement scan containing them shall return exit code `3` until reviewed. A Finding whose previously resolved fingerprint resurfaces shall count as new.

### FR-13: Coverage reporting

**[COVERAGE-001]** The bot shall report files or expressions it could not fully analyze. Unsupported dynamic expressions shall not cause false assurances.

**[COVERAGE-002]** Every Analysis Scope shall report these four independent coverage dimensions:

- **parse coverage:** successfully parsed eligible source bytes divided by discovered eligible source bytes, accompanied by parsed, failed, and total file counts;
- **style-resolution coverage:** resolved candidate style expressions divided by all detected candidate style expressions;
- **component-graph coverage:** resolved supported local UI edges divided by all detected supported local UI edges;
- **route coverage:** resolved route or page declarations divided by all detected route or page declarations.

**[COVERAGE-003]** Every dimension shall expose its numerator, denominator, ratio, policy status, excluded inputs, and unresolved counts grouped by stable reason code. Diagnostics shall identify affected paths or constructs without embedding unnecessary source. A zero denominator shall be reported as `not_applicable`, never as 100%.

**[COVERAGE-004]** The product shall not calculate or display a composite coverage percentage. It may display an overall categorical status derived from the explicit status of each required dimension. An `unknown` Page Archetype is a valid classification result and shall not reduce route coverage merely because no named archetype matched.

**[COVERAGE-005]** Advisory and enforcement scans shall both emit the complete coverage vector. Exit code `3` shall be determined by configurable per-dimension floors required by the active policy and enforced rules, not by a low AI Slop Score or low-confidence Finding. A dimension that is genuinely not applicable to all active rules shall not block enforcement, but its `not_applicable` status and denominator shall remain visible.

**[COVERAGE-006]** Discovery mockups and V1 defaults shall provisionally apply these coverage thresholds:

- parse coverage must be 100% of eligible source bytes unless files are explicitly excluded;
- style-resolution coverage warns below 90% and exits `3` below 75%;
- component-graph coverage warns below 85% and exits `3` below 70%;
- route coverage warns below 90% and exits `3` below 80% when a route
- or page-dependent rule is enforced.

**[COVERAGE-007]** The thresholds shall be validated against Calibration Cases and representative repositories before being treated as stable defaults.

## 8. Quality requirements

- **Explainability:** A maintainer can understand why every finding exists without reading scanner source.
- **[QUALITY-001]** **Epistemic clarity:** Reports shall keep aesthetic-convergence strength, static-analysis confidence, and analysis coverage distinct.
- **Precision:** Defaults should favor fewer, higher-confidence findings over a large volume of weak complaints.
- **[QUALITY-002]** **Performance:** On the committed reference runner, the scanner shall pass two separate cold workloads within 60 seconds and 1.5 GB peak memory each: one containing at least 2,000 representative supported source files and another containing at least 500,000 representative lines of supported JSX/TSX. Workflow setup and artifact upload time are excluded.
- **[QUALITY-003]** **Cache independence:** The performance budget shall be met without a persistent analysis cache.
- **[QUALITY-004]** **Progress overhead:** Enabling the normal interactive progress display shall add no more than 2% to elapsed analysis time on the reference benchmark.
- **Safety:** Analysis is source-non-mutating; only documented scanner artifacts may be written through the explicit artifact contract.
- **[QUALITY-005]** **Untrusted-input safety:** Scanning shall not execute target repository code or install its dependencies.
- **[QUALITY-006]** **Separation of concerns:** Aesthetic convergence, accessibility, semantic correctness, and prose quality shall remain distinct result dimensions.
- **[QUALITY-007]** **Privacy:** The core scanner shall not transmit source code or findings to an external service.
- **[QUALITY-008]** **No telemetry by default:** The product shall collect or transmit no usage or satisfaction telemetry; feedback export is explicit, local, redacted, and reviewable.
- **[QUALITY-009]** **Report minimization:** Default artifacts shall contain only the source evidence needed to locate and explain Findings, not full files or visible product copy.
- **[QUALITY-010]** **Portability:** V1 shall publish prebuilt native CLI binaries for Linux x86-64, Linux ARM64, macOS x86-64, macOS ARM64, and Windows x86-64. Users shall not need a Rust toolchain or Node.js runtime. Other targets may build from source without V1 support guarantees.
- **[QUALITY-011]** **Release integrity:** Every published binary shall have a checksum and be traceable to a scanner version and source revision.
- **[QUALITY-012]** **Release provenance:** Supported binaries shall carry verifiable build provenance and SBOM attestations tied to their release workflow and source commit.
- **[QUALITY-013]** **Compatibility:** Unsupported syntax or configuration shall produce actionable diagnostics.
- **[QUALITY-014]** **Evolvability:** Rule identifiers and JSON schema changes shall be versioned so downstream agents can rely on them.
- **[QUALITY-015]** **Upgrade transparency:** Rule-pack changes that affect scores or baselines shall be distinguishable from schema and binary changes and shall require explicit migration when incompatible.

## 10. Validation approach

**[VALIDATION-001]** Rules shall be tested against a labeled fixture corpus containing:

- intentionally over-styled examples;
- legitimate uses of individual effects;
- design-system components that centralize approved styling;
- shared primitives whose definition is questionable but whose many usage sites should not produce duplicate Findings;
- approved primitives used appropriately and used excessively or out of context;
- identical library components used in both deliberate and convergent compositions, proving package identity does not affect scoring;
- responsive and state variants;
- composed and conditional class expressions;
- CVA variants, common class-composition helpers, and configured wrapper aliases;
- mutually exclusive branches that must not create impossible signal combinations;
- repeated structures that are and are not appropriate abstractions;
- stock page structures in isolation and in convergent combinations;
- conventional page structures with distinctive hierarchy, brand treatment, interaction, or composition;
- positive, negative, and ambiguous cases for every built-in Page Archetype;
- custom and unrecognized pages that must receive generic analysis without forced classification;
- attributed, minimized public-project fixtures whose provenance and license metadata are testable;
- equivalent structural roles with varied wording, proving that prose style does not affect Bot 2 scores;
- visually similar examples with different accessibility quality, proving accessibility does not alter AI Slop Scores;
- malformed and partially supported source.

**[VALIDATION-002]** The calibration corpus shall have three complementary layers:

1. Controlled pairs that implement comparable UI content with a generic AI-default treatment and a deliberate alternative.
2. Repositories owned or selected by the Design Authority and labeled against the intended House Style.
3. A varied sample of public React/Tailwind projects independently reviewed by a small group of React maintainers.

**[VALIDATION-003]** The corpus shall be divided into a tuning set and a blind holdout set. Splitting shall occur by source repository and design family rather than randomly by component so paired, derivative, or visually near-duplicate cases cannot leak across sets.

**[VALIDATION-004]** Weights, caps, bands, archetype signatures, and default-policy decisions may use only the tuning set. Discovery gates shall be reported separately on the untouched holdout set.

**[VALIDATION-005]** A sealed holdout shall be used for only one release-decision cycle. Once its results are disclosed, any rule, threshold, or report revision influenced by those results shall be confirmed on a fresh sealed set drawn from new repositories or design families. Prior holdout failures shall remain in calibration history and shall not be erased by rotating or replacing cases.

**[VALIDATION-006]** Each Calibration Case shall retain:

- the source under analysis;
- a rendered image or other stable visual reference;
- expected and rejected Findings;
- acceptable exceptions and their rationale;
- reviewer judgments and disagreements;
- the scanner version and policy used for any result.

**[VALIDATION-007]** Permanent automated Calibration Cases derived from public projects shall be minimized, pinned to an original commit, and limited to sources with licenses permitting the intended use. Each derived fixture shall preserve source attribution, license metadata, and a link or identifier for the original revision.

**[VALIDATION-008]** Whole public repositories may be scanned separately during discovery but shall not become network-fetched automated test dependencies. The permanent suite shall run offline and produce deterministic inputs and expectations.

**[VALIDATION-009]** Rendered references support human evaluation of visual sameness but shall not be scanner input in V1.

Threshold changes should report their effect on the corpus. Real-world repositories and maintainer judgments are needed before default policy can be called stable.

**[VALIDATION-010]** Reviewer labels may be used to evaluate or suggest constrained changes to weights, caps, interactions, and band boundaries. V1 shall not train or embed an opaque statistical or machine-learning classifier.

**[VALIDATION-011]** Any calibration optimizer shall preserve monotonic constraints, interaction caps, unique-evidence accounting, explainability, and required counterexamples. Its output shall be a proposal requiring Design Authority approval and a semantic before/after diff across the complete Calibration Case corpus.

**[VALIDATION-012]** The accepted embedded calibration data shall remain sufficient to reproduce every score without reviewer data or an optimizer at scan time.

### Automated test layers

**[TEST-001]** V1 shall include:

- unit tests for extractors, static resolution, graph construction, rules, scoring, fingerprints, configuration, and policy;
- golden tests for canonical JSON, Markdown Refactoring Briefs, diagnostics, and progress-event sequences;
- metamorphic tests proving that irrelevant formatting, class-order changes, supported line-ending changes, and ordinary file movement do not alter semantics unexpectedly;
- property and fuzz tests around parser-facing resolution, malformed source, path handling, configuration, and report serialization;
- end-to-end CLI tests on every supported release platform;
- GitHub Action smoke tests using pinned binaries and artifact generation;
- time and peak-memory regression benchmarks;
- mutation testing focused on rule predicates, thresholds, score aggregation, coverage policy, baseline matching, and enforcement decisions.

**[TEST-002]** Test failures shall preserve minimized reproduction inputs where practical. Fuzzing shall not require executing target repository code.

**[TEST-003]** Traditional line coverage may be reported diagnostically but shall not be the primary release gate. Every rule shall have an explicit behavioral matrix covering:

- a positive match;
- a legitimate counterexample;
- a score-band boundary;
- House Style mitigation or approval;
- narrow Suppression behavior;
- partial-resolution confidence behavior;
- baseline regression behavior;
- stable explanation and canonical output.

**[TEST-004]** Rule and policy modules shall provisionally require at least an 80% mutation score. Surviving mutations shall be reviewed for missing behavior, equivalent mutations, or unjustified implementation complexity; they shall not be hidden by adding meaningless assertions.

**[TEST-005]** Golden artifacts may be regenerated only through a dedicated developer command. Regeneration shall produce a semantic diff summarizing changed Findings, AI Slop Scores, bands, confidence, Analysis Coverage, work batches, schema fields, and ordering.

**[TEST-006]** CI shall compare but never regenerate or accept golden files. Bulk golden changes without an explained semantic diff shall not satisfy review requirements, particularly after scoring, weighting, normalization, or rule-pack changes.

**[TEST-007]** The benchmark fixture, runner image, CPU allocation, scanner options, file count, line count, elapsed analysis time, and peak memory shall be recorded with performance results. Raspberry Pi/ARM measurements should be published when available but shall not block V1 acceptance.

**[TEST-008]** The CLI progress-display trial shall be evaluated alongside report mockups during requirements discovery. Candidate displays shall use the same underlying phase events so presentation can change without changing analyzer behavior.

**[TEST-009]** During requirements discovery, proposed examples and report formats shall be shown to intended users before implementation commitments are made. Evaluation shall collect at least:

- whether each proposed Finding is accepted, rejected, or considered ambiguous;
- whether its explanation identifies the real design concern;
- whether its suggested direction is actionable by a coding agent;
- whether important instances of aesthetic convergence were missed;
- whether AI Slop Scores match the user's comparative judgment among components within the same Analysis Scope and compatible policy;
- whether the resulting cleanup would increase satisfaction with the product's distinctiveness.

### Discovery gates

**[VALIDATION-013]** The Discovery Prototype may begin with the controlled evidence needed for its single Rule Contract. A rule shall not enter a releasable milestone until it passes the blind validation gates below. The Validated MVP applies the gates to Repeated Decorative Shell and Effect Stacking; Full V1 applies them independently to all eleven rules.

**[VALIDATION-014]** Each Rule Contract shall define its independent Calibration Case unit. Each rule's untouched blind holdout shall contain at least 20 independently labeled in-scope positive cases and 20 acceptable-counterexample cases, spanning at least eight source repositories and four design families overall, with no repository supplying more than 25% of either polarity. Tuning cases are additional and shall not count toward these holdout minimums. A case may exercise more than one rule only when each expected rule outcome is labeled independently. Results shall report both case-level metrics and repository-clustered metrics.

**[VALIDATION-015]** Every rule shall pass all of these gates on its blind holdout:

- **precision:** at least 90% of emitted high-confidence Findings are accepted as valid;
- **recall:** at least 80% of independently labeled, in-scope positive cases produce the expected high-confidence Finding;
- **useful yield:** across repositories containing labeled convergence, distinct high-confidence actionable Findings cover at least 70% of labeled affected components; duplicate Findings for the same rule, owner, and compatible state family count once;
- **brief actionability:** at least 80% of generated Refactoring Brief work batches can be planned by the intended agent or maintainer without reinterpretation of the reported design concern.

**[VALIDATION-016]** Precision, recall, and useful yield shall be calculated at the same default actionable operating point: a default-enabled rule, an unsuppressed Finding scored `moderate` or higher, high Finding Confidence, and `report` or `enforce` disposition. Low- and medium-confidence advisory Findings shall be reported separately and shall not satisfy recall or yield. All four gates, including actionability, shall be reported per rule; a passing aggregate shall not conceal a failing rule, and an implementation that emits too few Findings shall not pass merely because its precision is high.

**[VALIDATION-017]** Every Page Archetype family claimed as supported by Template Convergence shall additionally have at least 10 positive and 10 acceptable-counterexample blind cases drawn from at least three independent repositories in each polarity. Results shall be reported per family and repository cluster; no family may claim a false-positive rate below 10% from a sample whose outcome granularity cannot demonstrate that threshold. Unknown and custom pages shall receive a separate blind set covering both valid generic Findings and valid non-Findings.

**[VALIDATION-018]** Before the Validated MVP is released, exactly seven external React maintainers shall each complete a realistic cleanup-planning task using a report without implementation-team guidance. At least five of seven shall independently rate the report accurate, actionable, and worth using. Full V1 shall repeat the task-based gate with reports covering the expanded rule and archetype surface. A participant counts toward the threshold only by satisfying all three judgments; raw ratings, task outcomes, disagreements, and abstentions shall remain in the discovery record.

**[VALIDATION-036]** At least four of those seven maintainers shall complete the first-use workflow locally on a repository they maintain or a representative private or redacted snapshot. At least three of those four shall reach one accepted useful Finding and complete an initial triage decision within 15 minutes without implementation-team guidance. Evaluation shall record setup time, time to first useful Finding, triage effort, reasons for abandonment, intent to reuse, and willingness to consider advisory CI without collecting repository contents automatically.

**[VALIDATION-019]** Taste-specific disagreement shall be represented as optional or House Style policy rather than forced into universal defaults.

**[VALIDATION-020]** The Validated MVP shall run a predeclared set of at least ten representative agent-led cleanup trials covering its two-rule surface. Full V1 shall run a fresh predeclared set of at least ten trials covering the expanded rule and Page Archetype surface; MVP trials shall not satisfy the Full V1 gate. Each trial shall provide only the proposed Refactoring Brief and normal repository access to a coding agent working on a disposable branch or copy.

**[VALIDATION-021]** Trials shall use at least two independent coding-agent or model families. Comparable cases shall be distributed across them, and a small overlap set shall be attempted by both to expose agent-specific interpretation.

**[VALIDATION-022]** The overlap set shall include paired runs using the Refactoring Brief alone and using the same brief with Capability Requirements mapped to an available UI or design skill. Trials shall compare correctness, distinctiveness, behavior preservation, corrective prompting, and elapsed effort.

**[VALIDATION-023]** Skill mapping shall remain optional regardless of outcome. The paired evidence shall determine whether and when Refactoring Briefs recommend specialized capabilities.

**[VALIDATION-024]** The discovery record shall identify agent and model version, available tools, repository state, Refactoring Brief version, supplied capability mappings, corrective prompts, elapsed effort, and outcome.

**[VALIDATION-025]** Trials shall record whether the agent targeted the intended Slop Patterns, satisfied each Preservation Obligation, reduced perceived interchangeability, and required corrective prompting. Behavior and accessibility outcomes shall be checked independently through the applicable existing tests, configured verification, and human review; the scanner's score change shall not count as preservation evidence. The Design Authority shall compare stable before/after rendered references without being told which is which when practical.

**[VALIDATION-026]** At least eight of ten trials shall independently verify all required Preservation Obligations and be preferred as less convergent without material corrective prompting before the applicable release. Failed, unknown, and ambiguous obligations shall remain in the discovery record and shall drive revisions to report structure, capability requirements, preservation constraints, or rule explanations.

**[VALIDATION-037]** Trial protocols shall freeze the prompting rubric before execution. Factual clarification requested by the agent about an unknown Preservation Obligation or supplied House Style constraint is non-corrective; a prompt that restates or changes the intended design concern, points the agent to a missed target, requests repair of behavior the agent broke, or supplies an omitted remediation decision is material corrective prompting. A trial requiring any material corrective prompt shall fail the no-material-correction condition.

**[VALIDATION-027]** The agent-led before/after pairs used as evidence of general customer value shall be selected and frozen before trial outcomes are known, and each shall receive at least three blinded external React-maintainer reviews. Reviewers shall judge which version is more deliberate, distinctive, and appropriate to the page's stated purpose and House Style without being told which version is the cleanup.

**[VALIDATION-028]** At least two-thirds of external reviewers shall prefer the cleanup, alongside Design Authority approval and behavior-preservation checks. House-style-specific disagreement shall be recorded separately from failure to reduce generic convergence.

**[VALIDATION-029]** These are release gates for detector behavior and customer value, not claims of population-level statistical performance. Rejected and ambiguous cases shall be retained to refine rule boundaries, score interpretation, report language, and configuration before release.

**[VALIDATION-030]** The acceptance thresholds shall also be reported per Page Archetype. Aggregate results shall not allow strong performance on common archetypes to conceal an unsupported or unreliable built-in archetype.

**[VALIDATION-031]** The initial Design Authority shall label every Calibration Case and judge the first report prototypes. Before the scanner's default policy is described as generally useful, the seven-member external React-maintainer pool shall independently evaluate the material. Every sealed-holdout Calibration Case used to justify a universal default shall receive at least three external reviews before scanner outcomes are disclosed; reviewers may receive balanced predeclared subsets to keep the workload practical. Disagreements shall distinguish:

- a universal default candidate;
- an optional opinionated rule;
- a repository-specific House Style rule;
- a signal too subjective for deterministic enforcement.

**[VALIDATION-032]** Reviewers shall label Calibration Cases independently before seeing scanner scores, proposed bands, or other reviewers' judgments. Labels shall capture both classification and rationale.

**[VALIDATION-033]** Broadly agreed patterns may become universal default candidates. Split judgments shall become optional rules unless more evidence resolves the boundary. Judgments specific to the Design Authority shall become House Style policy. Unresolved ambiguous signals shall remain visible research evidence but shall not be enforceable.

**[VALIDATION-034]** A proposed universal-default classification shall require at least two-thirds agreement among its external reviewers in addition to the Design Authority's label. Meeting that threshold permits candidacy; it does not override the false-positive and actionability discovery gates.

**[VALIDATION-035]** The project shall retain disagreement data rather than replacing it with a forced consensus label.

### Design reference policy

*Refactoring UI* by Adam Wathan and Steve Schoger should be a major source for candidate heuristics, counterexamples, remediation language, and fixture design. Its practical, developer-oriented tactics fit this scanner's intended audience.

The maintained mapping from reference principles to rule evidence, protected counterexamples, remediation guidance, and human-only judgment is [the Refactoring UI traceability matrix](docs/references/refactoring-ui-traceability.md).

**[REFERENCE-001]** The book shall not be treated as a machine-enforceable specification or the sole definition of good UI. A tactic becomes a default rule only after it can be translated into observable source evidence, bounded by counterexamples, and validated against representative repositories. The project shall distinguish:

- principles that inform explanations and remediation;
- measurable signals suitable for deterministic rules;
- subjective advice that requires human judgment and must not be presented as certainty.

**[REFERENCE-002]** The repository shall cite the source of derived rule rationale without copying substantial proprietary text.

## 11. Preferred implementation stack

**[TECH-001]** The preferred implementation is a Rust-native scanner core and CLI using Oxc for JavaScript, TypeScript, JSX, and TSX parsing. Rule evaluation, repository and module graphs, scoring, configuration, and report generation shall remain in Rust rather than being duplicated across Rust and TypeScript.

**[TECH-002]** The GitHub integration shall be a thin composite Action that invokes a prebuilt scanner binary. JSONC configuration, JSON Schema, versioned JSON output, and Markdown output remain language-neutral public contracts.

This preference is conditional on a focused feasibility benchmark demonstrating:

- correct parsing and source locations for every supported syntax fixture;
- sufficient AST and semantic fidelity for the hardest class-composition, CVA, wrapper, import, route, variant, shared-component, and cross-file fixtures;
- no need to execute or install target repository code;
- parsing and graph construction for the 500,000-line reference corpus within 15 seconds and 750 MB peak memory;
- deterministic report output across supported worker counts;
- practical deterministic builds and GitHub Action packaging;
- successful creation and smoke testing of every required platform binary;
- composite Action execution without requiring the scanner or target project to install or use Node.js or target dependencies; GitHub-managed action infrastructure may use its own bundled runtime for checkout, cache, or artifact services;
- no project-authored `unsafe` Rust, with unavoidable unsafe behavior isolated to reviewed dependencies;
- a compressed release binary no larger than 30 MiB;
- acceptable implementation complexity for adding and testing rules.

**[TECH-003]** The benchmark shall compare at least a Rust/Oxc implementation with a pure TypeScript reference on representative hard cases. A TypeScript/Rust hybrid shall be adopted only if measured evidence shows that it improves the product without creating duplicated rule logic or costly AST marshaling.

**[TECH-004]** If Rust/Oxc fails a required capability, the decision shall be revisited explicitly rather than concealing the gap through guessed analysis.

## 13. Resolved working assumptions

The completed requirements interview establishes these working assumptions, subject to the validation gates above:

- the product begins as a local Rust CLI and later gains thin GitHub presentation layers;
- V1 ships prebuilt binaries for the supported Linux, macOS, and Windows targets, including Linux ARM64 for Raspberry Pi;
- GitHub Releases are the canonical binary channel, complemented by a pinned composite Action and optional `cargo install` support;
- the Validated MVP prioritizes whole-repository local analysis and an agent handoff; Full V1 adds whole-repository baseline regression enforcement, while changed-code-only presentation remains post-V1;
- React across the supported JavaScript and TypeScript source forms is the first framework boundary;
- Tailwind v3/v4 and static React inline styles are the V1 styling surfaces, behind an extensible extraction boundary;
- findings are advisory by default;
- deterministic static analysis is the complete core, with no LLM dependency;
- agent-readable findings recommend constraints and direction but do not generate patches;
- repository-specific policy is more useful than a universal definition of bad UI;
- the private initial design brief is a source of hypotheses, not an authority or distributable project material;
- customer satisfaction must be estimated from reactions to concrete examples and report prototypes, not inferred from the proposed architecture alone;
- the project owner is the initial Design Authority, while external React maintainers provide generalization evidence;
- House Style is supplied through explicit repository configuration; inference can only propose changes for approval;
- V1 configuration is declarative JSONC with a published schema; executable TypeScript configuration is excluded for security;
- V1 treats repositories as untrusted data and accepts explicit coverage limits rather than executing or building target code;
- V1 uses only rules built into the scanner binary; executable rule plugins are excluded;
- the built-in rule pack combines typed Rust mechanics with embedded, schema-validated calibration data;
- monorepository frontends are independent Analysis Scopes; the top-level report summarizes them without blending their scores;
- V1 reports the complete repository; a reviewed baseline is created only after the initial cleanup and later acts as a visible regression ratchet;
- the downstream agent contract is versioned JSON plus a generated Markdown Refactoring Brief, with no automatic patch generation;
- the first GitHub integration is an Action with report artifacts and a job summary; it does not post inline review comments or require a hosted App;
- the calibration corpus combines controlled pairs, Design Authority repositories, and externally reviewed public projects, with rendered references used only for human validation.

## 16. Requirement traceability and reproducibility

**[TRACE-001]** Every normative requirement containing `shall` and every numbered release acceptance criterion shall carry a stable, non-positional identifier with a semantic prefix. Once published, an identifier shall never be renumbered or reused; a removed requirement shall remain represented in history as retired. Explanatory prose and examples shall not receive identifiers merely to inflate coverage.

**[TRACE-002]** `docs/requirements-verification.md` shall map every active requirement identifier to its delivery milestone, planned verification method, required fixture, benchmark, review, or artifact, and current evidence status. A requirement without evidence shall remain visibly `pending`; narrative assertion shall not count as verification.

**[TRACE-003]** Performance and feasibility results shall reference a committed runner specification that pins or records, as applicable:

- operating-system image or container digest;
- architecture and CPU model;
- CPU quota and worker count;
- memory limit and swap policy;
- scanner build profile, version, and semantic options;
- corpus or fixture digest, file count, byte count, and line count;
- cold-cache preparation and measurement procedure;
- elapsed-time and peak-memory measurement tools.

**[TRACE-004]** The phrase “standard GitHub-hosted runner” shall not define a reproducible acceptance environment. A GitHub-hosted runner may be measured as supplementary evidence only when its image label, image revision, advertised resources, and observed hardware are recorded.

**[TRACE-005]** The scanner binary and analyzed target project shall not require Node.js. The composite GitHub Action may rely on GitHub-managed action infrastructure whose implementation uses a bundled Node.js runtime for platform services such as checkout or artifact upload; this shall not be described as a target-project or scanner runtime dependency.

**[TRACE-006]** Before implementation readiness and every release, an automated consistency audit shall fail on duplicate or missing requirement identifiers, missing verification mappings, contradictory milestone labels, invalid schema examples, undefined canonical glossary terms, incompatible or unresolved ADR status, and acceptance evidence that does not identify its requirement.
